    Testing Your Single-Cycle CPU

    We have assembled every piece into a working single-cycle CPU, but a design that looks right on paper is not the same as one that is right. Before we can trust it, we have to prove it. In this lesson we build a self checking testbench. It runs real instructions through the processor and compares every result against an independent reference, so that any mismatch is caught the instant it happens, whether it is a stray control signal, an off by one immediate, or a branch that goes the wrong way.

    What’s New

    When we tested the ALU, we already met the core idea behind good verification. We built a self checking testbench that fed the design a set of carefully chosen inputs, worked out the correct answer a second way using an independent model, and compared the two. If they ever disagreed, the testbench told us at once. We use that very same idea here. What changes is the size of the thing we are checking. The ALU is a single combinational block with no memory, while the CPU is a complete machine that runs a program over time. Testing a machine that remembers values and changes from one clock to the next asks for three new ideas.

    The first idea is that we now test time and state rather than a single snapshot. The ALU has no memory, so its test could hand it one pair of inputs, wait a moment for the logic to settle, and check the result once. The CPU is different. It holds values in its registers and its data memory, and it works through its program one clock at a time. To keep up with it, our reference model runs alongside the processor in lockstep. It carries out the same instruction the CPU is about to carry out, and after every clock edge we pause and compare. Instead of one check at the end, we perform a fresh check on every cycle of the whole program.

    The second idea is how much we look at. When we tested the ALU, we watched one result bus along with the overflow and zero flags, and that was the entire visible output of the block. A processor has far more state worth checking. After each instruction we compare the program counter, all thirty two registers, and every word of data memory against the reference model. If any one of them drifts from the expected value, even in a corner of memory the current instruction never touched, the testbench notices. We are no longer checking a single number. We are checking the entire state of the machine.

    The third idea is that we check the design against two independent references instead of one. The ALU test trusted a single behavioral model, and for a small block that was reasonable. For a whole processor we want more assurance, because a mistake could hide just as easily in our checking code as in the design itself. So alongside the lockstep model we add a second reference that is built in a completely different way. We work out the expected final state of the registers and memory by hand, write it into a table, and compare the processor against that table once the program finishes. When the hardware, the lockstep model, and the hand worked table all agree, we can be confident that the design is correct and that our test did not simply fail to notice a problem.

    These three ideas, checking over time, checking the full state, and checking against two independent references, are what set a processor testbench apart from a unit test of the ALU. Everything else carries straight over from the work we already did, from the self checking structure to the curated inputs to the pass or fail banner at the end. If you would like to see the full testbench, including every task and the complete set of results, the entire design verification report is available on GitHub.

    Choosing What to Test

    To test the processor we hand it a short program and let it run from beginning to end. The program is only about thirty instructions long, but it is written with care. Rather than a random pile of operations, it reads like a small computation. The early instructions load a few starting values into registers, and the later instructions build on those values, so each result feeds naturally into the next. This gives the test a real program flow, which matters because a processor is not just a set of instructions but a machine that carries values forward from one step to the next.

    The first job of the program is to use every kind of instruction the processor supports. It performs register to register arithmetic and logic with add, sub, and, or, and slt. It repeats those operations against immediate values with addi, andi, ori, and slti. It moves data to and from memory with lw and sw. And it steers the flow of control with the three branches, beq, bne, and blt. By the time the program finishes, every instruction the design claims to support has actually run on the hardware.

    Simply running each instruction once is not enough, because many instructions behave differently depending on their inputs. A set less than has to be tried when the comparison is true and again when it is false, so the program does both. An immediate add is given a positive immediate in one place and a negative immediate in another. A load is performed with a negative offset rather than only a positive one. There is even an instruction that writes to register x0, which the processor must quietly ignore, since x0 is permanently zero. Each of these is a separate case, and the program is arranged to reach all of them.

    Branches receive the most attention, because a branch has two outcomes that travel through different logic. If we only ever tested a branch that was taken, we would never confirm what happens when its condition is false, and the reverse is just as true. So each branch appears more than once. In one place the values are set up so the condition holds and the processor jumps to a new address, and in another the condition fails and the processor simply continues to the next instruction. A few instructions in the listing sit directly after a taken branch and are never meant to run at all. When the processor skips over them exactly as planned, that too is evidence that the branch did its job.

    Taken together, these choices form a coverage checklist. It names every instruction and every case we intend to reach, and as we write the program we make sure each item is accounted for. Anything left unchecked at the end is a gap we know about and can come back to fill. This is how a program of only thirty instructions can give us honest confidence in a processor that could one day run billions.
